## 4. Sim: new segment pieces ("features") and airborne physics

Design principle (same as the existing `landscape`/`quirks` work): every new field is **optional; absent = today's behaviour**; no new draws on `Rng(seed)`; new randomness uses its own `new Rng(seed ^ CONST)`; apply any new grip/speed factor in **both** the baked profile (`buildProfile`) and the live path (`traction()`, `gripLevel()`), and in the profile cache key (`Race.build()`, `race.ts:499-517`), or cars drift against a limit the profile didn't use.

### 4.1 Data model
Add to `Segment` (track.ts, beside `surface/bank/elev`): `fx?: { t0: number; t1: number; type: FxType; power?: number }[]` with `t` in 0..1 of the segment's length (or sample indices 0..24; pick one and document). `FxType` (all gameplay-meaningful, all render distinctly):
| type | gameplay | art |
|---|---|---|
| `jump` | ramp; take-off launches the car airborne (4.2) | wedge ramp with chevrons, shadow gap on landing |
| `boost` | speed pad: +`power` top speed/accel for ~1.5 s, no grip change | glowing arrow pad |
| `ice` | grip ×0.45 (new surface) | pale blue, glints |
| `sand` | grip ×0.7, top speed ×0.8 (new surface, desert/beach shortcuts) | dune texture |
| `mud` | grip ×0.6, top ×0.7 | dark brown |
| `water` | shallow water: top ×0.85, spray particles, kart sound hiss | blue overlay |
| `glide` | long jump (bigger air time, `power` scales distance), the "glider" ramps | larger ramp, wings glyph |
`ice/sand/mud` should be added to the existing `SURFACES` table (`terrainMul` mixing with `Vehicle.rough`) instead of a parallel mechanism where possible; `boost`/`jump` are new `Profile` per-sample arrays (`boost[]`, `jump[]` take-off marker) filled from `fx` in `buildProfile` and included in the cache key.
Anti-gravity, underwater sections, half-pipes, trick ramps: **cosmetic only** (map to `bank` + art tint/arrows); document as "approximated".

Free-circuit data format: each course in `kartdata.ts` = `{ points: number[]; fx?: {at:number /* metres along lap from start */; len:number; type; power?}[] }`. `buildFreeCircuit` converts `at/len` (metres → units via the circuit scale) into per-segment `fx`. Also allow per-course `surface`/`bank`/`tunnel`/`elev` through the same list (hills: optional `elev` keyframes by distance, e.g. Wario Stadium, Choco Mountain). Extend `landscape.test.ts:47-49` to exempt kart circuits (or assert only on non-kart circuits).

### 4.2 Airborne physics (the hard part; read `race.ts step()/traction()/collide()/hash()` first)
New `RaceCar` fields: `air: number` (ticks left, 0 = grounded), `airT: number` (total ticks of this flight, for the arc), `airV: number`. Behaviour:
1. **Take-off:** when a grounded car's `s` crosses a `jump` sample (profile `jump[]` marker) at speed `v ≥ JUMP_MIN_V` (slower cars just ride over the ramp as a small hump / no air), set `air = airT = clamp(AIR_BASE + AIR_K * v/vTop, AIR_MIN, AIR_MAX)` ticks (`glide` ×`power`). Deterministic, no RNG.
2. **In the air:** heading frozen (no steering), no braking, no throttle change, no traction, no tyre wear/heat/fuel use change beyond normal consumption; speed decays with `AIR_DRAG` (small) ; position advances along the **path** (`c.s += v*dt` as the profile-following model already does) so a car lands where its line says, but its lateral aim is frozen at take-off value (a car on a bad aim lands off-line, which can end in the grass, accepted).
3. **Landing:** `air` reaches 0 → normal; if lateral offset is outside the road (`half`) treat like off-road (existing recovery); landing from a high `airT` costs a small speed loss (`LAND_LOSS` ×(airT/AIR_MAX)) and, if the car is also turning hard, a spin check using the existing `settle`/spin machinery (`SPIN_CLOSING`), not new code.
4. **Collisions:** while `air > 0` the car is on level `LEVEL_AIR` for `apart()`; it neither collides with nor is blocked by grounded cars (and does not yield at junctions). Traffic logic (`trafficLimit`, dodge) ignores airborne cars and airborne cars skip traffic limits; both must be checked so nobody brakes for a car flying over them.
5. **Pits/limp/recovery:** an airborne car can't enter the pit lane or be "stuck"; guard `rec`/`stuck`/`held` counters (`air > 0` ⇒ treat as moving).
6. **Profile:** at a `jump`, the profile must (a) not brake into the ramp more than for the same straight, (b) cap `vLim` for the **landing zone** so a car launched at `vTop` doesn't land into a corner it can't take (author-time check in 4.4 prevents bad data; at run time add `LANDING_REACH = vTop*AIR_MAX*dt` of straight after each jump).
7. **Hash:** add `air` (and `airT` if stored) to `Race.hash()`; bump `SIM_VERSION` 3→4 **once, at the end**; update `tests/version.test.ts` GOLDEN (blind to race-only features, so the bump is manual) and `DEVELOPER.md`/`docs/DESIGN.md`.
8. **Traces for the renderer:** `Race.record()` must write an `atrace`/lift value per tick (0..1 arc height = `sin(pi*(1-air/airT))`) so playback can draw the lift (cf. existing `ptrace/gtrace/ftrace/ttrace`).
9. **Bots:** `botLine` needs nothing (kind-agnostic) but bots must not set lateral aim changes in the air (dodge is frozen) and should lift/straighten into the take-off (existing line smoothing is enough; verify with a headless run that 63 bots through a jump don't spin on landing).

Constants (starting values to tune headlessly with a before/after table): `JUMP_MIN_V` ≈ 0.45 vTop, `AIR_BASE` 18 ticks, `AIR_K` 30, `AIR_MIN` 12, `AIR_MAX` 70, `AIR_DRAG` 0.002/tick, `LAND_LOSS` 0.06.

### 4.3 Checks (checkTrack additions)
For every `jump/glide` fx: the segment must be `straight`-kind (or kink) and the next `LANDING_REACH` units must be on the road with κ below a threshold; no pit lane overlap; no obstacles in the take-off/landing zone (`placeFeatures` must skip fx cells like it skips `isCrossing`). Fail loudly at data-build time with the course id.

### 4.4 `fun-*` tracks get the new pieces
User: "Add any new segment pieces to 'fun-*' tracks." Implement as a **post-pass `funPieces(track, seed)`** run after `funLayout/applyWidths/makeBranches` on its own stream `new Rng(seed ^ 0x6b61727d)`:

- Per fun track: 0–3 `jump`s on long `straight` segments that satisfy 4.3 (not next to a fork/merge/bridge/cross), 0–2 `boost` pads on straights, and for biome-appropriate tracks one `ice` (snow), `sand` (desert) or `mud`/`water` patch on a straight or kink; at most one fx per segment, none in the first/last segments (start/finish and pit straights).

### 6.3 Tracing a layout (semi-automatic; quality gates decide)
Per course (script-assisted, with the implementer looking at each result; the agent can open images with the Read tool):
1. **Pull as much visual reference as possible for every course, not just the minimap** (user instruction: "pull images (or video stills) from each track to better approximate layout"). All into a **scratch dir outside the repo** (e.g. `$SCRATCH/mariokart/<id>/`), never committed, never shipped, never hot-linked:
   - Scrape the course page for *every* image: the map/minimap, the overview/aerial image, the in-game screenshots and the per-game map variants (`MK64_`, `MK7_`, `MK8DX_`, `MKT_Map_` prefixes). Get real URLs from the page HTML/file pages (the hash directories at `mario.wiki.gallery` are unpredictable).
   - Video stills: for each course find a gameplay/flythrough/"course preview" video (the wiki's external links, official trailers, or a search for "<course> flythrough/track preview"), download with `yt-dlp` (check it and `ffmpeg` are installed first: `command -v yt-dlp ffmpeg`; if missing, tell the user the install command rather than installing silently) and extract stills with `ffmpeg` (e.g. one frame every 2 s plus a frame at each jump/ramp/hazard), then build one contact sheet per course (the repo's own toolkit has `um video` contact sheets; or ImageMagick/Pillow). Prefer overhead/flythrough footage for layout and chase-cam footage for hazards, jump placement, width, scenery and theme.
   - Look at the images with the Read tool (it displays PNG/JPG), compare the minimap with the stills (which way the lap runs, where the start line is, which straights are long, where ramps/boost pads/water/ice/sand are, how wide the road is relative to the karts, hills), and record those findings in the roster entry (`features`, `theme`, `notes`) as text. Only the derived numbers and notes are committed.
   - Record in `docs/KART_CREDITS.md` that images/stills were consulted transiently as reference and none are included in the repo or the game; keep a per-course sha256 list of the reference files locally (not committed) so a run is reproducible.
   - If a video or image cannot be fetched (region/age block, 402, 404), say so in the PR and fall back to the wiki's text description plus other games' versions of the same layout; mark the roster entry `confidence: "low"`.
2. Extract the road centreline from the best map/overview (cross-checked against the stills): threshold the road colour (minimaps are high-contrast), skeletonise (Zhang-Suen) or use the existing `tools/circuits/trace.ts` if it accepts a polyline/raster (read it first; it is how lago-maggiore was traced), order the skeleton into one closed loop, simplify (Douglas-Peucker), resample ~every 12–20 units, choose the start line on the main straight.
3. Scale: units = metres × `scale`; choose `scale` so kart lap time ≈ 30–60 s and `trackLength` lies in 1200–7000 (tests); store the *shape*, not the image pixels.
4. Place `fx` by hand from the page's hazard list **and the stills/video** (jumps, boost pads, shortcuts, water, ice, sand), with distances along the lap read off the map/overview.
5. Validate with the same gates the tests apply, as a CLI (`tools/mariokart/check.ts <id>`): closed loop, `checkTrack` clean, `separation > 2*ROAD_HALF+4-0.5` between non-neighbouring segments, gate headings continuous, pit probe inside bounds, 3-lap 8-car race finishes, jump landing checks (4.3).
6. **Self-crossing/near-touching courses** (many SMK/MK64/DS/MK7/MK8 courses have bridges, crossovers, or parallel straights closer than road width): free circuits currently have **no crossing support** (only grid/fun layouts have bridge/under). Decide per course: (a) widen/shift the loop so it no longer crosses (`approx: "uncrossed"`, preferred, cheap); (b) for the few courses where the crossing is iconic (e.g. Toad's Turnpike no, but SMK Ghost Valley no; MK8 Mount Wario/Twisted Mansion/Electrodrome have overpasses), extend `freetrack.ts` with bridge/under levels (reuse `levelsOf/apart`, `bridgeDeck` art). Start with (a) for everything; track (b) candidates in a list in the PR description.
7. Commit only the resulting numbers (`kartdata.ts`), the roster JSON and the credits. Re-running the script must reproduce the file byte-for-byte (store raw image sha256 in the roster so changes are visible).

## 11. Risks and open points
- **IP/trademark:** official Mario Kart names and "Mario Kart" in a public repo + GitHub releases. User chose this knowingly; mitigations: no Nintendo assets/images/audio/characters/logos, disclaimer, official names isolated in one file, credits page. Mention in the final report.
- **Fidelity ceiling:** layouts come from a minimap + a text description by hand/script; expect "close approximation", not 1:1. Courses with crossings, multiple routes, underwater/anti-gravity/glider sections are approximated (4.1, 6.3-6). Rainbow Road variants, Wario Stadium etc. are separate layouts per game.
- **Counts and names in Appendix A are unverified** (the research agent's own total said 165 but its rows sum to 149; Booster Course Pass wave contents and Mario Kart Tour variants are from memory/unfetched). The implementer must re-derive the unique list from `Course_(Mario_Kart_series)` on the wiki and from the Booster Course Pass page, and keep a note of anything skipped.
- **Mario Kart World:** exists on the wiki; courses not enumerated here and not requested explicitly ("all the games"): ask the user whether to include it (and Mario Kart Tour-only layouts) before spending effort; battle courses excluded.
- **Airborne physics is a sim change touching hashing, traffic, collisions and bots** (SIM_VERSION 4; all existing leaderboard times are reset by the version rule, as with past bumps). Measure bots through jumps before authoring many courses.
- **Performance:** `kartdata.ts` ~150 KB is fine; `cachedTrack` LRU is 64; heavy tests sampled (6.4).
- **Kart pace** is low; scale courses so laps are 30–60 s, otherwise stars/AI skill tuning (`difficulty.ts`) may feel off; check `referenceTime` and difficulty stars on a few kart courses.
- The `Fandom` wiki is unreachable (HTTP 402); use mariowiki.com only. Don't hot-link images in the game.
